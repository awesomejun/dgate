# 외부 결정 계층 참조 — aptly·CAO 흡수 (2026-11-21)

dgate 게이트 설계(Neon §5)와 `DECISION_API` 평가에 가져올 것만 뽑은 참조 문서.
출처 스냅샷 검토: github.com/abruption/aptly · github.com/awslabs/cli-agent-orchestrator

## 두 구현이 일치하는 설계 신호 (독립 구현 2건 일치 → 높은 신뢰)
- 모드 3단계: `off` / `shadow`(기록만) / `on`(적용) — 모두 기본 off. dgate와 동일.
- 호출자 명시값 보존: 명시 모델·effort·권한은 결정 계층이 절대 덮지 않는다 (dgate 하드 가드 `requires_write`·`forced_split`과 같은 원칙).
- 멱등: 결정 1건 = 요청 ID 1개. 재시도는 같은 ID, 문맥 보충 재요청은 1회만.
- 판단 보류: `unsure`/`needs_context`면 적용 대신 기록·결정적 폴백. confidence는 보정 확률이 아니라고 명시(자동 적용 임계값으로 쓰지 않음).
- 로컬 선행: 정책·단일 후보·캐시·예산으로 판단 가능하면 API를 부르지 않는다 (CAO: `single_option` 기록 후 미질의).

## aptly — 전송 범위·비용 실측 계약
- 전송 범위 3단계(없음/작업설명/발췌), 미선택 시 전송 없음. 발췌는 `min(4000, 설정)` 바이트·첫 문단 원문. 재요약·익명화 금지 — 왜곡으로 잘못된 판정을 만들지 않기 위해서.
- 원문은 로컬 장부에 저장하지 않음(해시·메타데이터만). 진단 로그에도 원문 미포함.
- 비용 실측 프로토콜: 동일 고정 작업·동일 지시 → 기준 모델 대비 게이트 적용(분류비 포함), 캐시 반영·비반영 2종 환산, 표본 수·제외 항목·비보장 목록(품질 동등성·통계 유의성) 명시. — dgate `DECISION_API=on` 전환 판정에 이 양식을 그대로 쓴다.

## CAO — 결정 포인트·배달·청소 패턴
- 결정 포인트 분리: `model.route` / `effort.route` / `provider.route` + `task.features`(long_context·deep_reasoning·read_only·needs_network). 포인트별 off/shadow/on, 정책 ceiling/floor(명시 초과는 거부, 결정 답은 상한 캡·하한 상향), 폴백 순서(프로필 기본→정책 기본→공급자 기본).
- herdr·hc 백엔드 내장: 터미널 플레인은 우리 체계와 호환 — 전면 교체 없이 참조 구현으로 유효.
- 인박스 배달 3원칙: (1) 워커 상태 IDLE/COMPLETED일 때만 붙여넣기 (2) 제출 확인 — dispatch 시점보다 새로운 출력 스탬프로 실제 처리 시작 증거를 확인, 타임아웃 8초·최대 2회 재전송(전달은 됐는데 Enter가 삼켜져 보낸 사람이 영원히 대기하는 결함 방지) (3) 즉시 배달 + 감시(watchdog) 이중 경로가 같은 게이트로 수렴.
- kept-children 리퍼: 1분 주기로 유휴 창이 지난 종료 자식 정리 — 고아 워커 위생(고아 가시화와 짝이 되는 정리 축).

## dgate 적용 방향
1. 로컬 SQLite EWMA를 SSOT로 유지 — API decider는 고위험 분기(스웜 위임·편집·재시도·배포)만, shadow 먼저. Neon §5와 동일 결론.
2. 전송 범위 3단계·바이트 상한·멱등 요청 ID는 위 계약을 그대로 채택.
3. `on` 전환은 aptly 실측 양식(분류비 포함 환산)으로 판정한다.
4. 후속 후보(별도 승인 필요): 인박스 제출 확인·리퍼.

## 미채택
- aptly의 내장 서브에이전트 후킹: dgate 계약(내장 서브에이전트 금지, 외부 워커만)과 충돌.
- CAO 전면 도입: 결정 계층·로스터·TUI가 이중화됨. 참조 구현으로만 흡수.
